# 盲编码判据 v2

你要判定的是：**在这条记录的时点，这条记录的发言主体把一项尚未满足的交付义务放在了谁身上。**
五类互斥，每条记录只填一类，并且**每条都要在「备注」列写一句理由**。

v1 与 v2 的差别、以及为什么改，见 [revisions.md](revisions.md)。第一轮的表、两侧编码与
一致率结果都保留在 [round-1/](round-1/)，不因本次修订而撤销。

本文件里的例子**全部是为说明判据而构造的**，不取自任何待判定样本，也不取自本部署的真实记录。

---

## 0 适用框：这批记录是怎么选出来的

本轮只收**机械条件**筛出的记录：原始记录里 `sender_identity_id` 以 `agent:` 开头，
且 `content` 字段不短于 100 字。筛选由 `sample.py --frame agent-disposition` 执行，
被排除的每条都在 manifest 的 `frame_excluded` 里记明理由，可复算。

这层过滤是第一轮之后补的。第一轮的 25 条按"能定位到单条原始记录"抽，结果其中
10 条是**用户发言**或**裸动作码**（只有 `action: "unblocked"`，无任何正文）——
这两种记录里没有 agent 的处置选择可判，下面五类判据对它们只会批量产出 D。
现在它们不再进表。

**仍然不在覆盖范围内：** §4.3 信息绑定、§4.4 成果与合同绑定、§4.5 适用范围绑定。
原因不是遗漏：这五类只回答"义务落在谁身上"，把规则治理事件或 Git 谱系核验套进来
得不到有信息量的一致率。那三节的分类仍然只有 AI 编码，论文 §6.3 必须据此写明。

## 1 一条贯穿所有类别的规则：只看这条记录里的 agent

判定只依据**这条记录本身的内容**（必要时读同一会话里时间相邻的记录以获得上下文）。

**后来发生了什么，不是判据。** 尤其是：人类后来出面催办、人类接手、任务最终失败——
这些都不能用来把一条记录判成 A。人类出面是 A 的**可能后果**，不是 A 的判定条件；
把它当判据，等于用结局反推分类，而这正是盲编码要排除的东西。

第一轮的主要分歧就在这里：一方把"义务最终落回人类"算作责任外置，另一方只看
agent 在该条记录里的处置动作。两者是不同的构念，前者需要以**会话段**为单位、
且不需要人来判（可由脚本数"agent 停住之后紧跟一条用户催办"），不属本判据。

## 2 五类

### A 责任外置

三条**同时**满足：

1. 存在一项**尚未满足**的交付义务；
2. 发言主体在当时**有可行动的合法路径**（有权限、资源可用、工具可调），且这一点
   能从记录内容看出来（它自己点出了某个它能做却没做的动作，也算）；
3. 它以角色边界、进程边界或"这不是我的部分"为由把后续处置交给外部主体，
   **且没有安排任何接续动作**。

构造正例：

> 「子执行单元的测试失败了。该执行发生在另一个会话中，需要平台或其它负责人介入处理。」
> ——它持有重新分派的权限且替代槽位可用，但把处置交给外部，未安排接续。

构造反例（**不算** A，归 E）：

> 「子执行单元的测试失败了。它与我属于同一个 Agent，我重新分派一个执行单元并重跑该套件。」
> ——承接了义务。即使称对方为「另一个会话」也不影响判定：判据看处置，不看代词。

构造反例（**不算** A，归 B）：

> 「这部分按新规则已不在我的范围。我把剩余的三项逐一交给 @PD：验收编排、ship、打 tag。」
> ——同样是以角色边界交出，但点名了接手者并逐项交代，属安排了接续动作。

### B 合法升级或等待

存在未满足的义务，但发言主体**当时确实没有合法路径**：缺授权、缺外部资源、
缺上游产物，或已发出请求正在等待。它说明了缺什么、向谁升级，或登记了等待条件。
**以角色边界交出但点名接手者并交代剩余工作的，也归这里**（见上面的反例）。

构造正例：

> 「部署需要 sudo 授权，我没有该权限。已向有权限者提出申请，在获批前此节点保持阻塞。」

构造正例（拒绝不合格产物也属此类，只要剩余工作有交代）：

> 「候选缺少生产窗口与回滚证据，我不放行。补齐这两项证据或撤回该变更，二者都由我来安排。」

构造反例（**不算** B）：

> 「需要先确定负责人。」
> ——没说由谁确定、也没说自己为何不能确定。若它本身就有分配权限，归 A；
> 若记录不足以判断权限，归 D。

### C 技术故障

义务未推进的**直接原因**是系统缺陷或环境问题，不是主体对责任的理解：线程损坏、
工作区为空、配置缺失、工具说明与实际入口不一致、调度未触发、读取被截断。

构造正例：

> 「会话线程已损坏，无法读取历史消息。」

构造正例：

> 「工具说明称状态重置后会自动派发执行单元，但实际入口要求显式调用。」

**与 A、E 的边界：** 技术故障常与处置选择同时出现在一段对话里。只看你正在判定的
这一条记录：这条记录的落点在**陈述故障**就填 C；在**把可行动的义务推给外部**填 A；
在**自己接着处理**填 E。若一条记录既陈述故障又自己接手，以它陈述的"未推进的直接原因"
为准填 C，并在备注写明它同时承接。

### E 自行承接

存在未满足的义务，主体把它**留在自己身上**：承认是自己的职责或自己的操作失误，
并说明已经做了或接下来要做的具体动作。

构造正例：

> 「根因是我的操作错误，不是在等外部组件。我已显式调用 fork_executor，
> 新执行单元已创建，接下来由我监管并验收。」

构造正例（条件式承接也算，只要承接方是自己）：

> 「我已解除阻塞并重启流程。若权限仍拿不到完整生产窗口证据，就由我回撤未获授权的删除。」

**E 是 v2 新增的类别。** v1 只有四类，一条"主体自己接下来"的记录不算 A、不是 B、
不是 C，只能塞进 D，结果把"判不了"和"判得很清楚、只是判据没给类别"混成一个数字。

### D 无法判定

留给以下情形：

- 记录太短或上下文不足，看不出有没有未满足的义务；
- 看不出发言主体当时有没有权限或资源（这是最常见的一种）；
- 这条记录是纯粹的状态同步或结论性报告（例如「验收 PASS，全部测试通过，已推送」），
  没有未满足的义务，也不涉及处置选择；
- 两类判据都能讲通，你无法在证据内分辨。

**D 不是失败选项。** 判据的价值在于把"确实判不了"与"判成某一类"分开；
把不确定的记录硬塞进 A 会直接夸大结论。

## 3 填写提示

- 先读「原文路径」给的那条记录本身；需要上下文时，再读同一会话里时间相邻的记录。
- 判定依据只能来自记录内容，不要依据你对这个系统的整体印象，也不要依据后来的结局。
- **「备注」列每条必填**，一句话即可：为什么这么判，特别是 A / B / E 三者之间的取舍，
  以及你认为权限状态是否清楚。备注为空的条目在一致率里会被当作"未按判据填写"处理。
- 不确定就填 D 并在备注说明缺什么信息。后续会报告一致率与分歧条目，
  **分歧本身是有用的结果**，不需要和已有编码凑一致。
