# Agent Center四重点综合：保留能力，重新审查组织形式

2026-11-02。**单AI探索，尚未人工复核。** 本轮在006—008基础上补查Supervisor增量和流程信息变化，形成现阶段综合取舍；不是产品架构决策，不修改既有ADR，也没有实施简化或运行付费模型实验。

**现有证据支持的失败解释，是组织和流程形式没有自动兑现它们承诺的交付保证。** 有Supervisor不等于完整审查，有测试不等于覆盖需求，有完成节点不等于产品可发布，有图历史不等于保留代码成果。这些区别都有非调度bug片段支持。但排除明显系统bug后，仍不能证明S/E架构整体净负收益、流程复杂度导致模型认知过载，或单Agent一定更好。

因此现阶段应保留具体有用的能力：语义审查、必要的执行隔离、可核验产物、明确授权、共享事实、局部调整。对每个任务都固定经过多层LLM、每个执行单元长期人格化、每次拒绝都建新generation，分别审查必要性。不能把“尚未证明必要”改写成“已经证明无用”。

## 1. 本轮补做了什么

复用008的3个原生Plan包：Access新Plan、组织Graph、Spark开发，共100 Task/712消息；冻结198条定向时间窗口，筛选预览并深读关键链路，编码6个片段和4组结果转述，共41项不同原生记录。它们与既有案例重叠，不是新增加的独立样本。新增会话归属查询，使Task内重复、Task→Plan同步与跨Agent验收能够区分。[逐案报告](agent-harness-review-increment-cases-009.md)

从本地固定Git对象读取Access修复前后HTML/verify、Spark测试与持久发布报告，保存9份文件和8处证据片段。组织Graph三个版本的6份源码blob读取失败，保留原始错误；先前008的Git祖先/整树检查单独复用，不能冒充本轮代码复现。8个选定Task的execution mirror为0行，usage有28条report记录，但没有审查/转述对应的turn或S/E区分字段，不能估算本轮讨论的净成本。

“新增信息”只指**相对本轮可见记录的新增检查或判断**。自动delivery通知只给分支/SHA，不是完整executor输出，更不是Supervisor收到的全部模型上下文。历史消息写“独立核验”仍是参与者报告；本轮静态代码核对不能证明谁最早发现问题、验证命令是否全部执行或浏览器效果。

## 2. Supervisor究竟增加了什么

| 具体片段 | 增量 | 不支持的外推 |
|---|---|---|
| S01 Access canonical | 把Risk字段、typed-delete合同转成两项可操作拒绝；后续固定源码有对应修正 | 不能证明常驻Supervisor是唯一实现方式；没有恢复完整executor输入 |
| S02 Spark向导 | 常规测试绿时指出13类不能满足25类，测试阈值本身过弱；后续断言明确25个唯一ID | 不能把全部恢复归于审查，期间还有运行问题和代码工作 |
| S03 Spark成果继承 | 接受同parent同tree的不同SHA，拒绝遗漏已验收Web候选的后继 | 不是“只要一律强制祖先就好”；确定性核对与语义解释需区分 |
| S04—S05 组织Graph | Supervisor报告祖先、局部行为和回归检查；独立Tester继续补点击取证、跨project等遗漏场景 | 不能按PASS层数叠加可信度；各Task合同不同，也不能简单算Supervisor误判率 |
| S06 发布报告 | 接受完整发布矩阵报告，同时保持产品NO-GO | 任务完成不代表可以发布；合格报告可以给出否定结论 |

这些片段反对“Supervisor只是无用转述者”的绝对说法。它在部分时点确实承担合同解释和质量拦截。更值得简化的是**把所有职责捆在一个常驻LLM层里的默认组织方式**，但这是待比较的简化候选：现有观察尚不足以选择事件触发审查、独立Reviewer或原架构中的哪一种净收益更好。

确定性事实可以与语义判断分开：远端SHA、祖先/整树、候选是否可读、完成状态是可程序核验对象；“25个向导是否覆盖约定操作”“列表计数是否等于完整证据下钻”“报告合格是否意味着产品可发布”需要明确合同和语义判断。可自动核验不等于可以自动决定所有交付。

## 3. 哪些流程没有新增检查

选编的四组转述中，三组把Task结果同步到Plan，另一组是在同Task内约9秒后再次报告同一候选、修复、祖先和测试。**没有可辨识的新产品检查，不等于没有用途。** 跨会话传播结果、通知下游、保留审计和使人可读都有独立用途；也没有证据证明每条近重复文本都对应一次新的LLM推理或重跑测试。

这给出两条实际取舍：

- 重述同一结论不能计为第二份独立验证；展示多条PASS不应使证据看起来更强。
- 同一候选/合同/检查结果的通知可以考虑使用结构化结果引用与适量摘要，减少反复展开长段文字；这是简化候选，不是已经测出的节省。

另一方面，组织Graph的count检查→点击取齐两页→跨P1/P2 scope不是同一检查的机械重复；最终Reviewer没有发现新缺陷，但补充完整Go/integration/e2e范围，仍有验证用途。不能用“这一轮没找出bug”判断审查无效。

本轮没有找到足以量化“正常机制下纯无用LLM往返”的完整证据。大量更显眼的催办/状态解释来自陈旧告警、executor不可用、lease或调度问题，已退出设计负效应。不能为了得出负面结论把这些记录重新算进流程成本。

## 4. 四个研究重点的综合取舍

本表是研究建议。**保留能力不等于保留现有实现；简化候选不等于已获证实的新架构。**

| 做法或能力 | 当前取舍 | 依据与适用边界 |
|---|---|---|
| Task隔离执行、凭据边界、中心写入责任 | **保留能力** | S/E设计具有明确隔离/并发目标；本研究未证明这些边界无用，也未测得并发/安全净收益 |
| 对候选作语义和合同审查 | **保留，有条件使用** | S01/S02有具体纠正和代码对应；审查应绑定候选、合同、检查对象与证据 |
| 所有结果一律由常驻Supervisor重判，并持续转述给更多层 | **简化候选，组织形式待定** | 有价值的判断与可计算核验、同步职责混合；目前不支持全面删除，也不支持默认每层必要 |
| 独立Tester/Reviewer | **按不同覆盖面使用** | Graph补实际点击与跨project反例；职责、输入与测试差异重要，不是多一个角色名就有效 |
| 可读Agent名字与稳定身份 | **保留可识别性，分开建模** | 007用户偏好和身份/共享记录；显示名不应承担权限/记忆/会话边界的全部含义 |
| 每个临时执行器都长期命名、人格化 | **不列为自动交付必要条件；体验可选** | 未证明其自动交付增益；团队leader/掌控感是单开发者真实体验，不能被忽略或当效率 |
| 去掉名字就能共享context | **停止使用这一解释** | 多个命名Agent已有共享规则加载；应研究实际scope、权限、加载与会话边界 |
| 用局部PASS/任务done/重复PASS证明整产品成功 | **停止证据替代** | Access旧PASS、Graph局部覆盖和Spark报告NO-GO均表明对象与合同必须分清 |
| 在每次反馈后增加新任务/新generation | **不作为必需；支持原Task续修与只补证据** | Access有原任务修复；Mermaid代码报告早于改图；无法据此估计哪种更省成本 |
| 根据新事实局部调整DAG、保留等待与处置历史 | **有条件保留** | 008中有具体修复路径与正常资源等待；每次改图要说明改变了什么前提 |
| 用图节点继承替代产物继承 | **停止证据替代** | 008独立Git核验存在错基线；同树不同SHA反例也必须容纳 |
| 用generation/消息/任务数量判断效率或认知负荷 | **停止此测量替代** | 混有夹具、历史累计、同步、bug恢复、范围变更；没有可靠成本/认知归因 |

其中最有依据的“停止”，是停止错误的证据替代和未经验证的归因；不是凭个别失败直接裁掉整个架构。对于常驻Supervisor、多层审查、人格化执行单元，当前能说的是必要性或净收益未被证明，仍须按目标和证据选择。

## 5. 如何解释“整体不成功”

可以支持的机制链是：任务或角色的形式完成→被解释为更大范围已完成→真正需要的产品语义、候选继承或环境前提仍未证实→出现后续拒绝、用户改合同或剩余范围放弃。Supervisor、Tester和DAG有时发现并修正这些缺口；它们的存在本身没有消除缺口。

还不能支持的链是：名字多／流程多→模型认知过载→整个系统失败。它需要实际输入、上下文长度、任务难度、模型/版本、同合同对照等证据。用户对复杂和卡住的观察保留为重要研究起点，不能代替这条因果链的证明。

体验目标与交付目标应分别评价：用户获得“有一个团队、扮演leader、掌控感”的体验可以成立，同时全自动交付未达预期也可以成立。团队感不为低效辩护，自动交付不佳也不抹掉体验价值。

## 6. 剩余工作与停止边界

四个重点的**现阶段探索综合已形成**。剩余项按是否会改变取舍排序，不默认扩成大规模新研究：

1. 要决定是否取消常驻Supervisor，需同合同、同候选输入下比较其审查与更简单实现；现有可见摘要不够。付费实验仍需另定任务、评价、预算与停止规则。
2. 要把重复G9或错基线归因于机制复杂度，需完整读取/并发/工作区与运行版本记录；缺失则继续未知，不以更多同类状态日志替代。
3. 要讨论名字的因果收益，需保持角色/权限/context相同的对照；如只做当前工程取舍，现有“标签保留、人格可选、体验单列”已足够作为建议。
4. 人工抽查可提高关键案例可信度，但按用户授权不作为继续AI探索的前置。原产品视觉验收与历史运行均未独立重跑。
