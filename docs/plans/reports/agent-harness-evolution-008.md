# DAG evolution：有效调整、重复恢复与归因边界

2026-11-02。**单AI探索，尚未人工复核。** 使用既有冻结数据库和本地历史 Git 对象；没有重跑生产验收或模型实验。研究目的仍是解释设计实际价值，不要求创新点。案例时间统一为 UTC。

**本轮支持保留“根据新证据，局部调整后续工作并保留已有效成果”的能力。尚不支持把新增 generation 本身视为恢复成功，更不支持每次 REJECT 都重建一条链。** 真正产生进展的片段都有具体变化：修复代码、补上缺失检查、纠正候选基线、明确新产品合同，或把外部条件与后续验证分开。DAG 可以承载这些变化，但记录中的共同发生不能证明改图的独立收益。

两个特别明确的边界是：**图上保留已完成节点，不保证新候选保留了它的代码；换了提交 SHA，也不等于丢失旧成果。** 本轮分别找到并直接核对了这两种情况。另有五个重复节点的原生记录，但“读取截断”这一根因仅为参与者诊断，未排除系统问题，因此不将它计为正常 DAG 设计的负效应。

## 1. 范围与方法

沿用007的筛选规则：明显系统 bug 不进入设计负效应主证据；配置、运行版本未知、缺少外部资源及原因未明分别记录。普通被开发产品的缺陷是修复迭代的输入，不能因它是“bug”而排除所有代码修复；但若 harness 自身缺陷同时阻碍了运行，就必须拆开。没有重新纳入旧的 inline/fork、REJECT 后 ready、错误依赖传播等事故来证明复杂机制无用。

本轮先保存[协议](/Users/oopslink/works/research/agent-harness-study/run-001/evolution-008/protocol.md)，再导出与筛选。已知既有案例，不是盲评，也不是随机样本。

| 层次 | 覆盖 | 可以说明什么 |
|---|---|---|
| 全量结构盘点 | 108个Plan中32个有generation，共205条；含6个显式夹具Plan | 当前冻结记录的覆盖；无generation不等于从未live edit |
| 父子差分 | 32个根、173个子代；父代都存在且同Plan；170个子代改变节点/边，3个无拓扑变化 | 结构变化，不是170次有效恢复或3次无效操作 |

| 补充验证 | 原生任务/审计、固定设计文档、本地Git祖先/文件/整树关系 | 区分记录、设计意图和可复核的代码关系 |

快照任务常含累计历史；不能当同时活跃图大小。边按原生 `from_task_id → to_task_id` 表示前者依赖后者；字段缺失统一为默认值后比较。零悬空端点只表示快照引用的Task存在，不证明图可推进。`dispatched=null` 保留未知，不转换为零。[差分结果与方法](/Users/oopslink/works/research/agent-harness-study/run-001/evolution-008/derived/generation-deltas.json) · [32个Plan筛选表](/Users/oopslink/works/research/agent-harness-study/run-001/evolution-008/derived/plan-screening.json)

证据分三层：数据库记录证明“谁在何时说了什么、创建/废弃了哪些节点”；当时验收报告支持“报告了PASS/REJECT”，本轮没有独立复跑；本轮Git检查能独立支持指定提交的祖先、文件存在和整树相同。固定设计文档只说明意图。3个实现源码blob读取失败已留日志，不能据此推断实现不存在或部署版本如何。

## 3. 哪些“看起来在推进”没有相应证据

**重复创建同一条修复链，没有观察到新增交付。** Insight的canonical G9在19:46建立；20:06又新增五个G9节点，随后全部discard。一个节点曾进入running，不能说“完全没执行”或估算浪费了多少token。参与者说首次读取截断；本轮没有完整工具响应和并发执行trace，故只保留重复事实，不将原因写成LLM认知过载或DAG必然产生重复。[E04](agent-harness-evolution-cases-008.md#e04-insight重复五节点与保留有效候选)

**“保留旧节点”的漂亮承诺，单独不足以保住成果。** 组织Graph的G6仍保留G5历史，修复合同也要求基于G5；但本轮Git确认G5不是G6祖先，G5存在的Graph后端文件在G6不存在。后续G7及终验候选才确认继承G5。Spark也出现已验收Web候选未进入下游候选的情况。它们支持增加产物继承检查；没有完整执行输入，不能把错基线根因归给图设计，更不能声称已排除所有系统影响。[E02—E03](agent-harness-evolution-cases-008.md)

**“多了generation”不等于多了修复，也不自动等于折腾。** 3个零拓扑变化子代分别记录旧历史处置、继续已有恢复链、等待正式环境；最后一项明确拒绝创建可运行占位重试。这些是处置记录，不是代码进展。相反，组织Graph多轮验收确实新增不同反例，不能因为反复REJECT就统称重复劳动。旧Insight33代和Spark Host23代都混合运行问题、正常修复与范围变化，不作浪费排行榜。[差分审计](/Users/oopslink/works/research/agent-harness-study/run-001/evolution-008/derived/delta-summary.json)

**“后继done/PASS”不能追认旧合同完成。** Access新IA合同通过不恢复旧候选PASS；Spark向导局部通过不消除发布矩阵NO-GO；Spark Host当前done也不改变最后两项真实冒烟被废弃的事实。需要沿候选、合同、证据和目标谱系判定，而不是只看Plan状态。[004谱系方法](agent-harness-lineage-004.md)

## 4. 改图、代码、新信息和范围变化分别贡献了什么

| 因素 | 本轮能确认的作用 | 不能外推的结论 |
|---|---|---|
| 改图 | 新建或重接有具体输入/输出的后续工作，标明复验顺序、保留历史与外部等待 | 独立带来更高成功率；比原任务续修更高效 |
| 代码修复 | Mermaid修复先发生；Graph迭代补聚合/证据语义；Spark补齐向导；Access落实新IA | 新节点或更长链自己生成了修复 |
| Agent新增信息 | 浏览器失败、cursor反例、25向导缺口、Git基线关系、证据缺失 | 都是人工兜底；独立角色的净收益已被估计 |
| 人工补充信息 | 明确产品页、Mac多实例、可用制品基础设施；否定Access旧整页验收；重新指定测试职责 | 缺人工时必定失败；所有人工输入都是设计失效补救 |
| 验收范围变化 | Access两入口/Team Role属性；Spark Host平台与分发假设调整 | 同一目标、同一合同下的恢复成功率提高 |
| 环境与授权 | 真Linux/public-CA目标与sudo是实际执行前提 | 再改一遍图就能提供资源；正常等待是流程失败 |

上述因素在日志中相互伴随，不能做数值贡献分解。原生sender区分真实用户与Agent；`manual recovery`或“人工计划”字样本身不证明人类动手。组织Graph收尾的manual recovery由Agent报告，且伴随疑似交付检测问题，不能拿来论证设计必须依赖人类。[结构化因素表](/Users/oopslink/works/research/agent-harness-study/run-001/evolution-008/derived/cases.json)

## 5. 当前工程取舍

以下是基于案例的设计建议，尚未实施或经对照实验验证。

1. **保留局部改图，明确每次改变了哪个真实前提。** 新检查对象、可用候选、责任边界或外部条件至少有一项具体变化；仅把失败节点换ID不算交付进展。
2. **把已验收产物当作独立约束。** 除任务谱系，还记录候选SHA、祖先/完整文件树、已通过能力和适用验收合同。祖先关系也不是唯一标准：Spark同树不同SHA是必须保留的反例。
3. **支持原Task续修、只补证据、继续已有链和显式等待。** Access原Task修正和Insight保留候选说明，没有必要把所有反馈都升级为整条新链。尚不能断言哪种机制最省成本。
4. **变更验收范围时另记版本。** 把“旧缺口修好”和“用户重新定义要什么”分开；不让新合同PASS覆盖旧结论。
5. **避免用代数、节点数和done替代成果展示。** 它们可以保留作审计字段；对交付应展示有效候选、已证实能力、剩余缺口、等待的真实条件与被放弃范围。

未兑现的期待是“不可变历史＋自动换代就会自然连续地交付”。证据支持其中存在**产物继承、语义验收和外部条件**三个额外约束，不能由图结构代替。尚不足以认定DAG evolution整体无用、正常运行时净负担过大，或必须替换成单Agent。
