# Agent Harness：30个生产Plan的探索性分析

版本：0.2。研究日期：2026-11-01（America/Los_Angeles）。

**分析方式：单一 AI 分析者完成，尚未人工复核；没有独立重跑历史执行。** 用户已明确选择先完成全部探索性分析。本报告完成本轮30例编码与综合，不宣称完成确认性研究或因果验证。

## 1. 主要发现

当前最有证据支撑的主线是：**harness 暴露给 Agent 的动作提示、权限、执行模式、交付判定和终态规则不一致，会制造错误动作与恢复负担；DAG evolution 可以承接实质修复，也可能持续复制未解决的阻塞。**

这比“多层 Agent 让 LLM 认知混乱”更容易检验。本轮在历史源码中确认了一组动作提示与执行规则的矛盾，但没有证明层级数量本身造成失败。复杂分工也有明确发布记录，应保留为反例。

另一个重要发现是，**产品交付、验收结论和编排状态是三个不同结果维度**。done 可以表示拒绝收口；有些功能已交付但旧节点仍阻塞；有些旧 Task 失败后，同一目标由新 Task 完成。直接使用状态统计成功率会混淆这些情况。

## 3. 可复现的描述结果

以下是**非代表性样本中的观察标签**，可重叠，不是全系统发生率、故障归因比例或因果效应。

| 观察标签 | Plan数 | 解释 |
|---|---:|---|
| 流程/控制机制相关 | 24 | 包括状态、派发、恢复或交付判定；详见下述作用范围 |
| 有具体问题的质量门禁 | 14 | 记录显示门禁发现或拦截问题，实际运行真实性仍按E1/E2区分 |
| 针对明确问题的evolution | 13 | 有指向缺陷、前置条件或交付证据的改图说明，未证明因果收益 |
| 职责/权限/派发边界 | 9 | 规则、模板、权限或执行角色冲突 |
| 外部依赖 | 5 | 设备、授权、部署窗口或环境条件 |
| 重复演化且有重复阻塞叙述 | 3 | 不单凭代数高判定循环 |
| 上下文传递相关 | 3 | 包括有效共享finding和陈旧信息；不能读成3例context丢失 |

24例流程/控制相关标签中，19例指向当次运行中的问题叙述，2例主要是任务正在修复的harness功能，2例混合二者，1例是被审查候选中的规则缺陷。**Agent Center 在开发自身，任务主题中的bug不能全部当作当次执行故障。**

结果分类为：16例有集成报告、3例有部署报告、4例集成后部署待定；另外各1例为owner取消、Plan重建、验收转交未明确、验收结论撤销、替代Task交付、拒绝收口、部分交付。这些描述不构成23/30或任何其他成功率。

## 4. RQ1：复杂Agent结构与职责混淆

### 4.1 直接代码证据：建议动作与执行约束矛盾

I166 的消息 `01M2MV4NVZX2ZGBZH08MH0ZD0W` 记录：T2225 配置为 supervisor_inline，Agent却按执行状态提示重复fork；纠正为start_task后出现启动记录。

本轮读取了历史提交 `e59d7d52` 的两个文件：

- `execution_state.go:93–95` 对可用任务直接设置 `NextActionForkExecutor`，此分支没有按 dispatch_mode 区分。
- `executor_runtime.go:912–915` 对 supervisor_inline 明确拒绝fork。

这支持“harness接口之间存在可定位矛盾”。它不能证明该次所有409错误均由这条路径产生，也不能证明LLM内部发生某种认知状态；原始工具调用尚未回放。

### 4.2 模板与角色契约不一致

v2.16.0案例中，integration-dev说明自己执行Ship是因为节点确实指派给自己、Gate也已放行；PD确认模板默认指派与预期角色边界冲突。另有v2.10.3案例涉及三层分支规则未写清，导致集成和Ship职责错位。

**研究判断：** 多层结构可能扩大需要保持一致的边界数量；本轮直接观察到的是接口/规则不一致，尚不能把它与“层级数量”分离。角色契约、提示、权限、任务分配需要作为不同变量。

## 5. RQ2：工作流为何停滞

识别出四种值得进一步验证的具体机制：

1. **业务完成与控制面未完成冲突。** Plan Progress Control案例报告52/52有效任务完成，但旧stage condition继续阻止Plan结束；新增任务恢复frontier后，同类终态冲突再次出现。
2. **交付检测假阴性。** Collaboration Insight案例报告main已经有真实交付，eager-push却因分支名不符合synthetic约定判non_delivery，需要走恢复登记。当前支持来自参与者记录，需回放检测逻辑确认。
3. **拒绝被当作普通完成。** 节点移出不变量案例中，generation记录旧Ship因上游REJECT任务终态而错误放行；最终done明确只是“拒绝已收口”。
4. **候选分类规则误伤。** 编排P0案例的历史commit `7fd64337…` 扫描标题与整段描述中的verify、acceptance等泛词，推断evidence_only；审查指出普通代码任务会被误分类。该缺陷在源码中确认，但属于被审查候选，不应冒充生产故障发生率。

反例同样存在：Mermaid并发渲染、真实页面null崩溃、TLS兼容问题等记录显示验收发现了具体缺陷。删除门禁可能降低协调次数，也可能放过真实问题；本轮不能据此推荐全面取消验收。

## 6. RQ3：DAG evolution 的收益与边界

**正例候选：** Mermaid验收REJECT后追加修复与复验，最终修复commit `6855b0bd…` 及集成commit `b0c40b7c…` 在本地历史中存在；统一Access案例也有针对REJECT追加有界修复、最终单候选集成的记录。

**重复修复反例：** 旧Insight Plan累计148个Task、33条generation，记录了工具能力误解、部署控制不可用和类似链反复生成；最终被废弃，改建 `plan-929d9aaf`。

新Plan最初声明10节点短链，最终累计59个Task、12条generation。最终验收文件确实存在并包含PASS矩阵，但过程中仍发生权限、证据交付、候选验收问题。因此该对比仅支持“重新界定范围并持续修复后形成交付证据”，不能支持“改为简单结构就成功”。也不能把累计创建的59个Task误作同时活跃的59节点图。

两Plan由消息明确关联同一交付目标，共累计207个Task、45条generation记录；这是同一目标的累计记录，不是两次独立试验。代数差异也不能直接转成模型调用数、耗时或成本。

**研究判断：** evolution的作用应按“改变了哪个失败前置条件、保留了什么有效产物、产生了什么可核验新证据”评价。仅生成新任务并不保证恢复；保留并衔接已有交付是值得保留的候选设计原则。

## 7. RQ4/RQ5：名字、角色与情绪价值

本轮没有名字开关、角色开关或context共享方式的可比实验。日志中命名身份、模型、session、权限和角色绑定，无法分别估计它们的作用。

有两类有用线索：共享finding能够传递前置约束；错误assignee、跨项目派发和模板角色错位会形成恢复负担。它们支持研究上下文与权限的组织方式，不能证明名字本身妨碍共享。

对话中Agent之间的称赞、感谢和拟人化表达，不是开发者情绪价值的测量。用户提出的情绪价值观察在此作为研究假设保留。现有证据既不证明名字提高自动交付，也不证明其没有任何收益。

## 9. 设计假设与优先验证顺序

以下为研究建议，不是已批准的架构改动：

| 优先级 | 待验证假设 | 下一步实验 | 主要结果 |
|---|---|---|---|
| 1 | 一致的动作契约减少错误尝试 | 固定任务、模型和预算，只比较矛盾提示与一致提示；离线隔离运行 | 无效调用、恢复次数、独立验收、资源消耗 |
| 2 | 明确“新增证据”条件使evolution更有效 | 固定失败场景，对比直接重建与先核实前置条件变化 | 实际恢复、重复链、漏掉的可恢复任务 |
| 3 | 减少角色交接可降低协调成本且保留质量 | 保持等价质量检查，对比现有分工与较少交接 | 验收质量、遗漏缺陷、协调动作、成本 |
| 4 | 名字与context范围作用不同 | 分别切换名字、角色契约、记忆共享，不同时改变 | 信息遗漏、重复读取、交付；情绪另行评价 |

不以现有样本的频率安排统计显著性检验；实验需先固定任务集、预算、模型、样本量和停止规则。用户本轮选择探索分析，因此本轮没有启动生产策略变化、付费模型实验或历史运行重放。
