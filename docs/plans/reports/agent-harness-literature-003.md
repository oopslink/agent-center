# Agent Harness 文献比较与贡献定位

研究日期、文献截止：2026-11-01（America/Los_Angeles）。版本：0.3。

**单一AI分析，尚未人工复核。** 本轮完成围绕已有发现的定向文献比较，不是穷尽系统综述；没有独立复现论文实验，也没有新增生产干预。生产证据沿用[30例探索报告](agent-harness-research-002.md)。

## 1. 结论与推荐定位

原先五条观察中，**协调与职责错误、复杂流程的开销、动态工作流调整、角色与上下文组织、拟人化体验，都已有直接或邻接研究**。仅写成“多Agent太复杂、DAG evolution有用、名字没用”，不足以形成有说服力的独特贡献；最后一项也没有被我们的数据证实。

当前最值得推进的定位是：

> **生产Agent工作流中，跨Plan重建与验收变更如何影响交付结果的判定：一个纵向案例研究。**

其潜在价值是把同一交付目标下的编排状态、任务替换、历史契约、产物与验收证据联结起来，展示以单个Plan或最终状态计数会怎样误读恢复过程。**这是已有方法在具体生产问题上的扩展候选，尚不是已证明的新理论、新算法或首个此类研究。**

次要主线是把具体“建议动作—执行权限—交付检测—收口规则”的矛盾做成可回放案例。DAG evolution作为这些案例里的恢复机制研究，暂不独立主张提出新方法。姓名与开发者情绪价值保留为后续独立问题。

## 4. 最接近的先行工作如何限制贡献表述

### 4.1 “契约错位”不能直接包装成新失败理论

HarnessFix已经把trace中的数据流、控制流和实现锚点关联起来，针对不同harness层限定修复范围并进行回归验证。它也讨论保留部分工作如何改变后续验证与收口条件。HarnessTester明确把跨组件契约用于测试构造。因此，**trace + code + artifact、跨层归因、契约测试本身均不是我们的新颖性**。[HarnessFix，§III–VI](https://arxiv.org/abs/2606.06324v2)、[HarnessTester，§6](https://arxiv.org/abs/2610.04921v1)。

我们已有的较强材料是`plan-523d5d71`：历史源码一侧提示fork，另一侧禁止对supervisor_inline执行fork。它提供具体系统中的静态矛盾证据；若补上当时可见输入、真实调用和确定性回放，才能评价这个矛盾如何产生错误与恢复负担。另一个泛词误分类案例属于被审查候选代码，不能混算为已上线运行故障。

### 4.2 “终态不等于成功”也已有明确评价方法

TraceTrial-Bench区分Agent任务结果与harness可靠性，要求按问题选择外部状态、模型可见返回和产物等不同权威证据；还保存父子Agent与session的执行谱系。A2A失败研究也将环境状态、产物正确性和行为分层。因此，**分层结果、证据来源区分、执行谱系都不是空白**。[TraceTrial-Bench，§2–3](https://arxiv.org/abs/2610.32285v1)、[A2A-Failures，§2–4](https://arxiv.org/abs/2610.19342v2)。

我们的差异候选是具体生产语义：done可以表示拒绝收口；旧Plan废弃后目标由新Plan承接；旧验收可以撤回或改变适用范围。这需要追踪“谁对哪个版本的什么交付作了何种判定”，而不只是增加一个成功标签。是否足够形成方法贡献，需要实际显示它改变了哪些可审计结论。

### 4.3 “恢复要带来新证据”有很强的先行覆盖

Failure as a Process已经分析错误起点、锁定、无效修复和成功中的恢复；ToolMaze把恢复能力、最终完成和恢复开销分开；AgentTether直接研究诊断后如何维持纠正，甚至指出重复guard可能让Agent持续重规划。不能将“针对根因而非盲目重试”当作首次发现。[失败过程分析，§II–III](https://arxiv.org/abs/2607.09510v1)、[ToolMaze，§3.5](https://arxiv.org/abs/2606.05806v1)、[AgentTether，§IV–V](https://arxiv.org/abs/2607.06273v1)。

更接近的StateWise还保存经核实的持久纠正及修订谱系，并检验跨任务延续。因而“跨任务保留证据”也不能独立作为创新。我们的候选空间必须收窄到**同一交付目标在管理对象替换和验收契约变更中的延续**。[StateWise，§3–5](https://arxiv.org/abs/2610.05241v1)。

### 4.4 真实生产数据不是自动成立的独特贡献

Measuring Agents in Production已有部署实践访谈与调查；SWE-chat已有大规模真实开发会话、checkpoint与commit关联，并研究用户纠正和代码留存。我们的优势不在“首次真实数据”或规模，而可能在同一系统的**内部编排状态、历史规则、交付物和验收记录能够相互核对**。[MAP，§3、5–7](https://arxiv.org/abs/2512.04123v4)、[SWE-chat，§2–5](https://arxiv.org/abs/2604.20779v2)。

这种纵深也有代价：单系统/单开发者背景，时间与版本混杂，只有30个探索Plan且相互依赖，缺少完整逐步trace和人工复核。不能用案例频率与大样本研究比较总体发生率。

### 4.5 “交付目标谱系”需要承认过程挖掘先行方法

对象中心过程挖掘早已指出单一case ID会扁平化多对象事件；后续工作用相关对象图定义process execution，并展示同一申请下多个offer被取消、替换或接受。我们的旧新Plan现象有明显方法相似性。[对象中心过程挖掘](https://doi.org/10.1007/978-3-030-30446-1_1)、[Cases and Variants，§IV、VII](https://arxiv.org/abs/2208.03235v1)。

因此不能说“首次把多个任务归到同一目标”。可争取的贡献是适配Agent交付的关系类型、验收版本与证据规则，以及证明这些规则在真实记录中解决了什么测量问题。一个项目的所有Task不能仅因图连通就合成一个目标。

## 5. 独特贡献候选及当前成熟度

| 优先级 | 可争取的贡献 | 已有本地证据 | 还缺什么 | 当前判断 |
|---|---|---|---|---|
| **1** | 面向Agent交付的跨对象、跨验收版本重建协议及案例 | 4条不同类型的显式关系；旧新Insight的207个Task/45条generation；后继Task没有plan_id；撤销验收/拒绝收口案例 | 冻结归并规则，扩大关系核查；与Plan-only读法比较实际判定差异；人工复核 | **最值得推进的应用方法与实证贡献候选**，不是首创谱系 |
| **2** | 生产控制契约冲突的可复现机制案例 | I166历史源码矛盾；候选分类规则；若干运行中的角色/终态叙述 | 保存当时输入与调用；最小回放、修复对照、回归；区分部署故障与待审候选 | 可形成机制证据与基准案例；尚未证明新的通用缺陷类别 |
| **3** | 区分有效恢复与反复改图的生产过程测量 | 针对性修复、无效重复和复杂流程成功反例；已有产物/验收文件 | 重建代际diff与语义前提变化，追踪产物/纠正是否被使用；可靠资源分母 | 辅助贡献候选；不能宣称新DAG算法或已证实收益 |
| **4** | 姓名、功能角色、context和开发者体验的分离评价 | 开发者观察及角色/共享线索 | 独立操纵、体验数据、控制任务/模型/权限/预算 | **研究问题，当前不是研究发现或贡献** |

207个Task和45条generation是同一目标跨两个Plan的累计记录，既不是同时活跃图大小，也不是token或恢复成本。4条关系也不是4个独立目标：其中一条只是验收转交，不能自动当作全Plan替换。相关证据见[探索报告§6–8](agent-harness-research-002.md)。

建议论文贡献写成三个相互支撑的部分：**纵向生产案例；明确局限的交付证据重建协议；少量可回放的契约矛盾及其影响**。若后续重建不能改变实质判断，或回放无法成立，应降为经验报告，而不是扩大措辞维持新颖性。

## 6. 下一轮需要冻结的分析规则

以下是研究协议候选，不是产品领域模型改动，也不是本轮已经执行的测量。

### 6.1 保留不同种类的关系

以明确的交付要求为分析锚点，记录目标与Plan、Task、执行、generation、artifact、verdict及其适用版本的关系。至少区分：同目标承接、Task替换、验收转交、范围修订、验收撤回。每条关系保存原始ID、证据、时间、推断等级和未知项。

仅有同项目、相似标题或时间相邻，不足以自动合并。既有目标被缩小或更改时，保留原始与修订契约，分别描述是否满足；不能拿修订后的PASS证明原需求已完成。

### 6.2 用并列结果和可用证据评价

分别记录管理终态、可访问产物、验收结论及范围、集成、部署（若适用）。这些维度不是单向等级：验收可以被撤回，取消可能合理，已部署也可能未满足原需求。报告参与者自报、可读取证据与研究者独立验证的区别。

先在有证据的目标内比较Plan-only与关联重建的结论是否不同；逐案列出漏计后继产物、误把拒绝当成功、重复计入同一目标、验收适用范围错误。正式分母应是冻结后的可判定目标数；未知单列，不用当前30个Plan直接估成功率。

### 6.3 评价evolution的具体变化

每个恢复片段记录：原阻塞前提、改图差异、外部条件是否改变、已有产物/纠正如何延续、下一条可核实证据、最终或删失结果。新增证据可以是排除错误假设或确认无法继续，不限于PASS；重复一段不同措辞不算新证据。

“新增证据”不能机械变成奖励数量：额外检查也可能冗余。只有在可观察窗口中，前提未变、重复操作且没有新证据时，才标记重复恢复候选；日志缺失应为unknown。资源先报告可核查的控制动作/Task/generation，不能用它们冒充token成本或反事实浪费。

### 6.4 按依赖顺序继续

1. **目标谱系与验收版本重建**：从4条既有关系扩展，保留反例和未能确认的关系；先产出逐案判定差异表。
2. **最小机制回放**：优先I166的建议动作/dispatch矛盾；固定历史规则与输入，区分静态冲突、可复现错误和端到端影响。契约测试参考HarnessTester，证据结构参考HarnessFix/TraceTrial。
3. **恢复片段深读**：在目标层核对generation变化、前提及产物，保留实际质量门禁有效的反例。
4. **独立复核与受控实验**：人工复核仍未完成，当前按用户要求继续AI探索；如进入付费模型实验，先形成明确的任务、预算与停止规则。姓名/体验不混入前述实验。
