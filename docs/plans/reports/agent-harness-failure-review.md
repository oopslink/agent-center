# Agent Center 失败复盘与设计取舍

更新日期：2026-11-02（America/Los_Angeles）。**单AI探索，尚未人工复核。** 当前综合至009轮：四重点形成现阶段综合取舍，补查Supervisor增量与流程转述；新增固定代码对照、会话归属和成本数据可用性审计。继续排除明显系统bug；尚未确定各组织形式的净收益。原始数据、反证与前后版本保留。

**研究目的：解释 Agent Center 为什么没有达到预期，哪些方案没兑现收益，哪些值得保留或简化。创新点不是必要条件。** 四个重点仍为 Supervisor/executor 架构、名字的本质与必要性、机制流程复杂度、DAG evolution。

## 1. 当前判断先受一个范围限制

用户新增要求：**研究应该排除明显的系统 bug 导致的问题。** 当前主分析只用能够与这些 bug 分开的片段讨论方案价值。配置错配、外部资源缺失和根因不清的运行问题也单独处理，不将它们直接归因于组织结构或流程复杂度。

上一版以 inline/fork 冲突、终态卡死、REJECT 后 ready 等作为主要失败解释，混合了实现可靠性与设计价值。**这些事故仍是真实研究记录，但不能继续承担“Supervisor/executor 或复杂流程本身不行”的结论。** 历史006报告没有覆盖改写；当前取舍须使用[007追溯筛选](agent-harness-identity-cases-007.md#006轮追溯筛选)。[协议修订](/Users/oopslink/works/research/agent-harness-study/run-001/identity-007/protocol-v2.md)记录了范围改变发生在部分分析之后。

| 旧主要片段 | 当前研究地位 |
|---|---|
| I166 inline 提示 fork、执行合同禁止 fork | 明显实现/合同冲突，排除方案负效应 |
| v2.16 Ship 责任与 Git 工具能力不匹配 | 配置/指派单列，不能据此判定角色分工无效 |
| Progress Control 旧 condition、终态收口及循环前提 | 实现问题或原因未隔离，退出设计负效应主证据 |

不能将“系统总体没有达到预期”的开发者观察，直接提升为四个设计机制都已被证伪。筛选后，当前还没有足够证据估计内部 S/E 的净收益、得出它应全面废除，或认定复杂度导致模型内部“认知问题”。这不会改变研究目的，但会改变哪些结论可以写。

## 2. 排除 bug 后，仍有意义的观察

**语义判断不能由流程完成标志替代。** Access 案例中，用户否定了局部检查后形成的整页 PASS，后续更换验收范围与版本。它支持继续研究局部子任务结论如何被误外推到交付目标；目前不能排除上下文遗漏、提示不足或具体模型判断的影响，更不能单例归因内部 S/E。[004验收版本重建](agent-harness-lineage-004.md) · [006-C05](agent-harness-division-workflow-cases-006.md)

**独立角色曾带来具体收益。** Mermaid 的 Tester 在回归全绿时发现浏览器渲染失败，并对修复后 SHA 复验；v2.10.3 的 integration 根据远端事实拒绝重建已有 trunk；v2.14 的 Dev finding 补充真实 SQLite/schema/NULL 差异并有后续修正报告。这些正例的收益在新增事实、不同检查视角和具体产物，不在名字字符串。它们不能估计净收益，也不能用六月跨 Agent 角色合作证明后来的内部 S/E 架构有效。[007-N03](agent-harness-identity-cases-007.md#n03-专业角色与共享事实的正例)

**共享知识有真实的治理与加载选择。** memory proposal 归并、Curator 授权、规则索引、正文按需读取、快照刷新分别承担不同职责。230 条规则正文加载审计覆盖12个命名 Agent，提供命名身份与知识共享可以共存的原生证据；不是模型遵守率。治理步骤存在并不证明它们无用，也未测出净成本过高。[007-N04—N05](agent-harness-identity-007.md#4-真实案例哪些价值留下哪些假设尚不成立)

**团队体验有直接正面证据，不能当作自动交付指标。** 开发者自述“就是好像给了一个团队，可以扮演团队 leader， 有掌控感，上瘾”。它支持单开发者的团队感、领导者体验和主观掌控感；名字、角色、团队界面与指挥反馈同时存在，不能分离命名的因果效应，也不作成瘾诊断。[007-N06](agent-harness-identity-cases-007.md#n06-开发者直接体验)

**DAG evolution有具体用途，但自动换代不等于自动修复。** Mermaid的代码修复报告早于改图约46秒，图补齐正式复验路径；组织Graph各轮验收新增cursor、多effect与跨project反例，局部迭代不是同一问题机械重复；Spark在原25向导合同下补齐13→25，不能叫新增范围。另一方面，图上保留旧成果节点未能保证新候选继承代码，本轮Git核实了错基线与缺文件；同样也核实Spark不同SHA可以具有相同父提交和完整文件树。不能只看节点保留、SHA变化或代数判断成果。[008专项](agent-harness-evolution-008.md)

**有些恢复不需要新generation，有些完成只是放弃剩余范围。** Access一次局部REJECT在原Task原分支补代码后通过，没有新增generation。Insight确有五个重复G9节点，但读取截断的根因未知，退出设计负效应；不能作为认知过载已证实的例子。Spark Host最后两个真实设备验证节点因清理而discard，当前done不证明全矩阵通过。Access更换IA后的PASS也不能回填旧合同。[008逐案与反证](agent-harness-evolution-cases-008.md)

**Supervisor有具体语义增量，但不自动保证验收完整。** 009核对固定Git版本，Access审查提出的Risk字段与删除确认问题确有对应修正，Spark向导测试从至少12项改为25个唯一ID及长度断言。组织Graph中，Supervisor局部PASS后，独立Tester仍补出点击取齐两页、跨project scope反例。这支持按检查能力使用审查；不支持按层数累计可靠性，也不能因不同Task的PASS/REJECT就直接算Supervisor误判率。[009逐案](agent-harness-review-increment-cases-009.md)

**没有新检查的消息可能在做同步，不能直接叫浪费。** 009选编四组同候选转述：三组Task→Plan同步，一组同Task近重复。无可辨新产品检查不等于无通知/审计用途，也不证明额外LLM调用或测试重跑。8Task有28条usage，但缺S/E和具体消息/turn关联，不能估计这种往返成本。简化候选是减少长篇复述、使用结构化证据引用，而非删除结果传播能力。

## 3. 设计取舍工作表

下表是研究判断，不是已实施的产品变更。不能把“没有证明收益”写成“已经证明无用”。

| 方案 / 期待 | 排除明显 bug 后的证据 | 当前取舍 |
|---|---|---|
| Supervisor＋executor 隔离复杂性、提高并发 | 隔离/单写者有明确意图；009语义审查有代码对应正例，但局部PASS仍有覆盖遗漏；没有净收益比较 | **保留能力，组织形式待定。** 拆开执行隔离、确定性核对、语义审查和通知；常驻逐项重判是简化候选，不据旧bug负例全面废除 |
| 增加协调和复核就能持续自主交付 | Access提示语义覆盖仍须检验；多轮记录和完成状态不能单独证明交付 | **收益尚未充分证明。** 继续找正常机制运行下的无新信息交接；不能由消息多直接判浪费 |
| 专业角色使质量更好 | 独立浏览器检查、远端核验、schema finding有具体正例 | **有条件保留。** 绑定职责、输入、能力和授权；角色名不替代这些条件 |
| 精细状态/gate 保障推进 | 旧主负例多为状态和调度 bug，已剔除；独立检查的质量收益仍可观察 | **不作整体无效结论。** 评价正常 gate 是否增加新信息及其等待是否必要 |
| 每个 Agent 都要长期名字和人格 | 可读标签有反复用户偏好；持久人格未证明为自动交付必需；无匿名对照 | **可读标签保留，自定义队友体验可选。** 不要求每个临时执行器人格化 |
| 名字导致 context 不共享 | 固定源码按稳定 ID/scope/权限/快照组织知识，多个命名 Agent 有共享加载记录 | **该归因不成立为当前结论。** 单独评价身份与会话/知识边界的绑定；删名不等于共享 |
| 团队感、掌控感代表自动化价值 | 开发者明确有此体验；未有对应交付改进数据 | **体验价值与交付分别评价。** 不抹去体验，也不以体验替代结果 |
| DAG evolution 帮助恢复 | 局部修复/复验、保留健康候选、明确等待有正例；代码可先于图；每次REJECT不必增代；重复建链根因未隔离 | **有条件保留。** 改图须对应真实前提变化；支持原Task续修/只补证据/等待，不把新增代数当恢复 |
| 保留图历史就能保留成果 | Graph与Spark存在前置候选未被下游继承；另有同树不同SHA的反例 | **单独不足。** 配合产物继承与已通过能力核验；不以SHA不同判丢失，也不把错基线直接归因DAG |

“全员共享全部 context”“去掉所有身份”“把所有流程压成单 Agent”均不是本轮已验证的替代方案。应该保留的能力与可以简化的组织方式仍须分别检验。[名字专项完整取舍](agent-harness-identity-007.md#6-是否应该有名字分目标的工程判断)

## 4. 人工参与要按用途与真实操作者区分

旧案例中的催查 bug、纠正工具能力、恢复运行状态，不再计入设计本身需要人工兜底的证据。Access 的产品验收否定仍保留为用户纠正案例；记忆范围、work_type 是否硬编码、产品范围及停止扩展属于产品/设计决定；提供设备和授权属于外部条件。不能把后两类全部叫作失败补救。

同时，inline start、force_completed、manual_recovery 和所谓“人工硬门禁”中的多项实际操作者是 Agent。按 sender/actor 身份判断，不按“PD”“手动”“人工”的措辞计数。当前没有全量人工依赖率、人工工时，或没有用户时的反事实结果；正常权限拒绝也不能当作命名角色失效。

008进一步区分：Spark Host用户新增Mac/多实例、要求本地制品服务，是产品与现实基础设施信息；sudo、真实Linux与public-CA是外部前提；Access用户否定旧整页PASS并明确新IA，改变了验收合同。图可以表达这些变化，不能自行提供授权、设备或产品决定。上述Plan仍有用户参与，不能因某个修复诊断由Agent完成就称整个交付全自动。

## 6. 当前综合与剩余验证

四个重点已形成[现阶段综合取舍009](agent-harness-synthesis-009.md)：保留语义审查、必要隔离、可复核产物、明确授权、共享事实和局部调整；按差异覆盖使用独立Reviewer；可读标签保留、人格与团队体验可选；不把每次拒绝增代或每层LLM重判当必需。最有依据的停止项是错误证据替代：局部PASS不能替代整产品验收、图继承不能替代产物继承、重复PASS不能冒充独立验证、消息/代数不能冒充成本。

对常驻Supervisor、多层流程和人格化执行单元，应分别保留“有具体用途”与“默认必要性未证明”两种判断。现有证据不能宣告S/E整体失败、DAG整体无用，或单Agent一定更好。综合建议不是产品架构变更，没有修改ADR或实现。

剩余只补会改变取舍的证据：完整模型输入与候选工作区来源；重复G9的读取/并发；同合同同输入下原架构与简化审查、原Task续修与改图的可比结果。缺失则维持未知。付费比较仍须明确任务、评价与预算；人工抽查可提高证据强度，按用户授权不作为探索前置。
