# Agent 的名字、角色与 context：必要性复盘（007）

2026-11-02（America/Los_Angeles）。**单AI探索，尚未人工复核。** 本轮完成名字专项，并按用户最新要求追溯筛除明显系统 bug。研究目的仍是解释方案的实际价值与失败原因，不要求创新点。

**目前支持保留可读名字和可选的团队体验，但没有证据证明每个工作单元都需要一个持久人格。也没有证据证明名字本身改善或损害自动交付。** 名字、身份、角色、权限、记忆和本次 context 必须分别评价。已有命名 Agent 共享知识的实际记录，不能把知识隔离直接归因于名字。

## 1. 先收紧研究范围：明显系统 bug 不用于判定方案失败

用户在研究过程中明确：“研究应该排除明显的系统bug导致的问题”。因此本轮保存了[协议修订 v2](/Users/oopslink/works/research/agent-harness-study/run-001/identity-007/protocol-v2.md)，这发生在部分检索与阅读之后，不能冒充事前注册。旧协议、原始数据和旧报告均保留。

按**片段及其所支持的主张**筛选，而非整个 Plan 一刀切：

| 证据类型 | 当前处理 |
|---|---|
| 明确的身份键错配、解析/状态合同错误、能力未接线等 | 排除出方案负效应主分析，保留排除台账 |
| 缺工具、错配权限或指派等配置问题 | 本轮保守单列；不直接推出角色或架构无效 |
| 原因或运行版本未知，仍可能是实现 bug | 标为不确定，不承担设计失效结论 |
| 机制按预期运行仍有语义误判、信息选择或治理负担 | 可以研究；仍需检查模型输入、目标范围和替代解释 |
| 独立检查确实补充事实、发现交付物缺陷 | 保留正证据。发现被开发代码的缺陷，不等于研究因编排器 bug 而卡住 |
| 偏好与自述体验 | 单独分析，不能换算为交付质量 |

这个限制会实质性削弱上一轮部分负面结论。inline/fork 冲突、REJECT 后 ready、依赖未被调度消费，不再用于证明 Supervisor/executor 或复杂流程本身失效；旧 condition/终态矛盾、lease 恢复与分支交付诊断也不能在根因未隔离时承担该结论。[006追溯筛选](agent-harness-identity-cases-007.md#006轮追溯筛选)

排除不是声称这些事故没发生，更不是把它们换一个“设计问题”的名称重新纳入。当前缺乏足够的非 bug 证据，不能据此认定多层架构净收益为负。

## 2. 数据、检索与可识别性

沿用 run-001 的冻结 SQLite 快照，仅只读提取。全量 26,961 条消息执行三组固定正则检索，获得 835 条去重候选；类别重叠，名字/体验 390、记忆/context 308、身份路由 150。它们是词法命中，不是 835 个故障，也不表示逐条完整深读。

对命中的全部 33 条 user 消息逐条筛选：23 条为偏好或设计输入、7 条不相关、1 条转述、1 条 bug、1 条机制说明。名字类别的 15 条 user 命中也包含 Plan 名称、RAM role 和转贴诊断，不能全部当作命名体验。后续目的性选择 19 个锚点并提取相邻消息，得到 90 条去重上下文消息；再读取目标 Plan、既有案例包和固定历史源码。定向编码 **42 个证据用途，来自 41 项不同源记录**，组织为 6 个主主题和 3 个排除主题；重复引用不是独立观测。[检索、筛选与阅读范围](/Users/oopslink/works/research/agent-harness-study/run-001/identity-007/reading/coverage.md)

另外提取 16 个 Agent 的安全配置字段、29 个 Identity、成员/角色/授权关系以及全部 230 条规则加载审计。快照中 16/16 的 Profile.name 与 Identity.display_name 对应一致，14/16 有团队角色，1 个身份同时任 PD 和 PM；Dev 和 Tester 都存在多个不同名字的成员。全部 capability_tags 为空只说明该元数据未填写，不能推断没有工具能力。这些是快照状态，不是每个事件发生时的配置。[身份—角色映射](/Users/oopslink/works/research/agent-harness-study/run-001/identity-007/derived/identity-role-map.json)

**没有匿名对照组、随机改名、同任务同模型的角色消融，也没有完整的模型 turn 输入。** 名字多为项目/角色标签，不能把它们当作人名人格与匿名执行器的受控比较。重命名审计的空查询结果也不证明历史从未改名，因为查询表并非完整 Identity 变更史。

## 3. 六种概念实际承担什么

| 维度 | 本系统可核实的机制 | 本轮判断及边界 |
|---|---|---|
| **名字** | 可读显示、指代、导航与部分 mention 匹配；Profile.name、Identity.display_name 可更新 | 帮助人与系统交互；字符串不是能力证明。当前代码要求非空名字，不等于理论上每个执行器都必须有人格名字 |
| **稳定身份** | Agent 实体 ULID 与 Identity member ID 有显式映射；消息归属、运行目录与授权引用稳定键 | 支持连续归属和审计。保留身份引用，不要求把每次执行包装为长期队友 |
| **角色** | 团队成员关系独立存 role；同角色可多人、同身份可多角色；Description 是否进 prompt 另有开关 | 表示职责与检查视角。标题、提示词、真实专长与能力是不同变量 |
| **权限** | memory 仓库访问按身份/团队；canonical 提案处理另受 Curator 应用权限约束 | 名为 PD 不自动获授权；拒绝越权可以是机制正常工作 |
| **记忆** | Agent 本地目录按稳定 ID；另有 team/project/task 等作用域及共享规则仓库 | 知识可随任务或团队组织，不必与显示名绑定；共享存储不等于共享全部私有记忆 |
| **本次 context** | 由执行/会话、scope、阶段、规则 commit、选择与预算组成；在途执行可保留快照 | “存在”“有权读”“加载索引”“读取正文”“模型使用”是五种状态，不能混同 |

依据为固定历史对象中的 [16项源码证据](/Users/oopslink/works/research/agent-harness-study/run-001/identity-007/reading/source-evidence.md)：S01—S05 核对名字、身份、路径和描述传递；S06—S11 核对 scope、权限、加载及快照；S15—S16 核对加载审计定义与去重存储。每项附 commit、行号、全文副本和哈希。源码只解释给定版本可实现的机制，不能证明每次生产执行用了它。

因此，“给 Agent 起名”至少有三层含义：给对象一个可读标签；让用户容易建立持续关系；把长期职责、私有记忆和独立会话捆成一个队友。前两层可以保留，同时单独决定第三层是否值得。删除显示名本身不会合并记忆目录、扩大权限或把上下文自动传给另一个执行器。

## 4. 真实案例：哪些价值留下，哪些假设尚不成立

### N01：用户需要可读辨认，不要求用名字作为唯一机器主键

6月15日用户要求 Agent 使用名字并可点击查看详情，6月29日进一步要求所有页面优先展示名字，8月21日要求 at Agent 使用名字。7月3日则明确提出消息用 ID、展示时转换为名字，并希望 @name 与 @id 功能等价。这里有直接的产品偏好证据：名字有辨认、指代与导航价值，同时可以把显示和引用分开。没有可用的操作耗时或错误率比较，不宣称量化效率提升。[N01 六项证据](agent-harness-identity-cases-007.md#n01-可读名字界面与寻址偏好)

### N02：PD、身份与 Curator 权限不是同一件事

8月13日 03:09 UTC，PD 报告可读和提案但不能 promote/reject。快照中同一身份的 Curator 记录创建于 04:10；06:42 同一 PD 报告已完成处理。这一时序支持权限独立于称呼的解释，但记录创建时间不是完整授权事件史。拒绝未授权操作按正常边界保留，不能编码为“角色组织失效”或“名字没用”。[N02 三项证据](agent-harness-identity-cases-007.md#n02-身份角色与权限可以独立变化)

### N03：独立角色有具体收益，名字的额外作用没有被隔离

v2.14 中 Dev 共享真实 SQLite 表结构、NULL 索引等差异，后续出现具体修正报告；系统还向下游注入 19 条 finding。Mermaid 中 Tester 在回归全绿时发现实际浏览器渲染失败，之后对新 SHA 做复验；其所在 Plan 的 ready 调度 bug 另行排除。v2.10.3 中 integration 根据远端事实拒绝重建已有 trunk，纠正上游解释。这些价值来自新增信息、不同检查视角和事实核验。既不证明所有分工都划算，也不证明必须使用这些名字。[N03 六项证据](agent-harness-identity-cases-007.md#n03-专业角色与共享事实的正例)

“独立检查有用”也不自动支持“每个 Agent 内都应有 Supervisor＋多个 executor”：六月跨 Agent 的合作早于后来的内部 S/E 架构，分析层级不能互换。

### N04—N05：共享知识的负担在治理、选择与版本，不是名字字符串

8月13日用户询问堆积的 memory proposals 如何处理。PD 报告 20 条存在重叠，提出归并和替代关系；后报告 8 promoted、12 rejected、pending 为零。用户继续追问规则怎样进入成员 context，并担心膨胀，反对给每个节点硬编码 work_type。后续方案转为短索引、按需正文、commit 绑定与加载审计。

这里可以确认共享知识需要筛选、去重、授权、选择和刷新语义；不能确认这些工作净成本过高，更不能从“20条提案”推导浪费。提案正文/Git memory 仓库未独立取得，处理结果仍是参与者报告。早晚报告中规则数量不一致，不用于精确库存或模型失忆判断；用户的膨胀担忧也不是已观察到的性能下降。[N04、N05 原始链](agent-harness-identity-cases-007.md#n04-共享记忆需要筛选与治理)

Rule Registry 的 Plan 中，Tester 报告以 100×32KiB 合成规则正文进行验收，execute 索引为 25 条、小于 16KiB；integration 报告相关成果进入 main。它支持当时做过有边界的机制验收，**不是本轮重跑结果，不是生产 token 节省，也不是 LLM 交付提升**。integration 同时核实候选提交实际是 siblings，纠正上游所谓串链，提醒共享叙述仍需事实校验。[N05-E06—E08](agent-harness-identity-cases-007.md#n05-共享存储索引正文与本次context不同)

原生 `team_rule_load_audits` 共有 **230 条**，覆盖 **12 个命名 Agent、2 个团队、8 个规则 commit**，时间为8月14日至9月21日 UTC。其中 Agent Center 团队 228 条、11 个 Agent、6 个 commit，分 execute 123、plan 38、review 40、recovery 27；另一团队 2 条。它提供“不同名字的 Agent 已经通过共享机制读取规则”的数据库证据。[聚合及原始加载记录](/Users/oopslink/works/research/agent-harness-study/run-001/identity-007/derived/metrics.json)

按固定源码 S15—S16 的合同，230 条是具体 commit 下规则正文读取的持久审计，重复键不会再次插入；不是全部 API 请求次数，更不能换算成 230 次执行、230 次有效遵守或完整 context 相同。也没有证据证明每个 Agent 私有记忆都被其他成员可见。对“名字不利于 context 共享”的原始判断，当前应改为：**若持久身份被同时用作知识和会话边界，需要单独评估这些边界；显示名并不构成共享的必然障碍。**

### N06：团队 leader 体验是独立的产品价值

开发者在本次研究中直接回答：

> 就是好像给了一个团队，可以扮演团队 leader， 有掌控感，上瘾

保存为 [U007-01](/Users/oopslink/works/research/agent-harness-study/run-001/identity-007/raw/developer-reflection.json)。这是一位开发者的回顾性自述，没有提供具体日期事件，也没有量表或使用频率记录。“上瘾”按原词记录，不作临床判断。

自述支持三点：感觉拥有团队、可以扮演领导者、主观掌控感与吸引力。解释性假设是：可识别队友、角色分化、下达任务与收到回应共同形成这一体验。**不能把联合体验全部归给名字，也不能把掌控感等同系统的实际可控性。** 名字可能是这一体验的载体之一；单独改名是否改变感受，现有资料不能回答。

这项价值无须靠自动交付成功来证明自身存在。但若产品目标是全自动开发，不能以团队感、互动量或用户愿意继续指挥来替代有效交付。是否产生过度信任、过长投入或额外成本，本轮没有相应证据，不能从“上瘾”一词继续推断。

## 6. 是否应该有名字：分目标的工程判断

以下是由机制和有限案例提出的取舍建议，未改变产品，也未估计方案净收益。

| 选择 | 自动交付 | 开发者体验 | 当前建议 |
|---|---|---|---|
| 可读标签＋稳定引用 | 方便追溯；没有额外交付增益估计 | 用户反复明确偏好 | **保留**。允许自动生成可读标签，显示名不替代稳定引用 |
| 自定义队友名字与团队呈现 | 没有单独质量/速度收益证据 | 有单开发者直接正面自述 | **作为可选体验保留**，用体验证据评价，不要求每个临时执行器人格化 |
| 角色职责与独立验收视角 | 有补充事实和发现缺陷的正例 | 便于理解分工；未单独测量 | **有条件保留**，说明职责、输入、输出、授权与检查依据 |
| 名字自动代表能力或权限 | 名字和角色字段不能提供真实工具/授权保证 | 可以形成期待，但实际效果未测 | **不要依赖这种假设**；能力、授权和实际委托显式核对 |
| 每个角色固定绑定长期私有 context | 无证据证明普遍必要，也未证明普遍有害 | 可能强化连续队友感，仍未隔离因果 | **不作为自动交付的必选前提**；按任务连续性、隔离需求与知识可复用性决定 |
| 全员共享全部 context | 未验证；存储共享不能消除选择、预算和版本问题 | 未研究 | **不据本轮直接采用**；优先区分共享事实与当前执行所需输入 |

目前没有证据支持“去掉名字就能解决复杂流程或知识共享问题”。更值得后续验证的是：保留可读名称和必要稳定身份时，能否减少无新信息的交接，并让任务需要的知识在合适阶段可见。这里的“值得验证”不是已经发现这些交接无用。

## 7. 对综合复盘的修正及下一步

本轮把原先捆绑的名字、角色、权限、记忆和 context 拆开，也将 bug 驱动的失败片段从设计负效应中剔除。留下的非 bug 问题更有限：Access 把局部检查当整目标 PASS 的语义偏差仍可作为待核实案例；共享知识需要治理与选择；团队体验不等于无人兜底的交付。Access 仍缺独立视觉复核，不能把它单独升级为内部 S/E 的因果结论。

下一项按计划研究 **DAG evolution**：先按同一规则筛除明显系统 bug 与正常外部等待，再比较改图是否改变了真实前提；把代码修复、用户新信息、范围调整与图修改分开。若筛选后有效负例不足，报告证据不足，不把排除事故补回分母，不把 generation 数当成本。

完整保全包含原始选择字段、查询、筛选、证据指针、固定源码、排除理由、探针输出、开发者原话、协议修订、文档前后版本和校验清单。未修改生产代码/数据、未触发 Agent 或付费模型实验。本轮能说明可观察的用途与取舍边界，不能提供命名/角色的因果效应或群体体验结论。
