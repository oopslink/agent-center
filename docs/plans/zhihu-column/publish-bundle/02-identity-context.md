# 一个 Agent 到底是谁：身份、角色、名字与上下文的四种边界

> agent-center 是一个组织多个 AI Agent 协作完成软件开发任务的系统。Agent 在其中接收目标、调用工具，参与实现、检查与交付。《Agent 协作手记》以这个项目的开发和运行记录为线索，讨论各模块的设计选择、实现效果，以及实践中暴露的问题。

*Agent 协作手记 · 第 2 篇*

## 一、需求动机

项目有过这样一段规则整理记录：一名被称为 PD 的成员准备把经验提案发布成团队正式规则，第一步却收到 `not_memory_curator`。它在消息中说明，当前账号可以读取和提交提案，但不能批准或拒绝提案，因此没有继续改动提案状态，而是请求由具备权限的账号处理，或为自己补充授权。[治理权限案例：研究工作稿 P3 §4.2](https://github.com/oopslink/agent-center/blob/main/docs/plans/reports/papers-010/p3-role-shared-context/paper.md)

这里的 Curator 指被授权管理团队规则的主体。PD 是团队使用的职责称呼，却不自动包含这项权限。后续记录中出现了同一身份的 Curator 授权行和提案处理报告；这与“治理权需要单独授权”的解释一致，但不能仅凭这几条记录重建所有授权变更。

这次拒绝不是系统认不出成员，也不该为了让工作继续就取消检查。它把平时容易混在一起的几件事分开了：名字帮助人辨认成员，身份让系统持续识别同一主体，角色描述职责，权限决定具体操作是否允许。**一个成员被称作什么，与它实际获准做什么，需要分别核对。**

同样的区别也存在于改名和重启中。显示名可以变化，运行进程也可以更换，历史任务仍应关联到原来的业务身份；反过来，知道“这是同一个人”，也不能推导出它有权处理所有项目或所有治理操作。

即使身份和权限都处理正确，成员也可能无法完成任务。例如测试 Agent 有权验收，却只拿到了上一版代码的测试报告。它缺的是本轮判断所需的材料。本文把模型本次作出判断时实际能看到的任务说明、消息、文件和检查记录称为“上下文”。拥有身份和权限，不等于已经获得充分的上下文。

这篇文章围绕这几种容易混用的概念展开：系统怎样让成员保持稳定身份，怎样把名字、职责和权限分开，以及怎样为具体决策提供相关材料。后面的实现与实验会分别检查这些目标，避免用“像一个团队成员”笼统代替可验证的要求。

## 二、方案选择

这里有两类不同的选择。工程上，需要决定身份、组织关系和执行配置怎样关联；交互上，我们也曾期待稳定的个人名字能增强团队感，甚至改善协作。后一种期待需要独立检验，不能用来替代身份和授权设计。

任务要在 Agent 改名、重启、转派之后仍能查到负责人。把显示名当作任务键，改一个名字就会牵连历史记录。用临时进程标识也不合适，重启后进程会更换。系统因此保留稳定的业务身份，把组织角色和执行配置分别记录。这样做增加了一次身份映射，却让成员可以换配置、保留历史，并按组织关系接受权限检查。

当前代码里至少有三层容易被统称为“Agent 身份”的对象。Identity 是用户或 Agent 的账户身份，带稳定 ID、种类、展示名和账户状态；Member 是 Identity 与 Organization 的成员关系，带角色和状态；执行侧的 Agent 聚合带 Profile（运行配置）、Worker（承载执行的工作节点）绑定、生命周期与身份关联。Task 的 `assignee` 则是任务面向某个 actor 的引用。[代码：Identity](https://github.com/oopslink/agent-center/blob/main/internal/identity/identity.go) · [代码：Member](https://github.com/oopslink/agent-center/blob/main/internal/identity/member.go) · [代码：Agent](https://github.com/oopslink/agent-center/blob/main/internal/agent/agent.go) · [代码：Task](https://github.com/oopslink/agent-center/blob/main/internal/projectmanager/task.go)

![身份、组织关系、执行配置与上下文的分工](assets/05-identity-map.png)

图 1：边界示意。四项分别回答识别、授权、执行与判断材料的问题，不能互相替代。

这些边界需要分别记录。成员关系可以变化，执行 Agent 可以停止或换配置，展示名可以编辑，任务归属可以转移；稳定身份不应该随着任何一个变化而丢失。运行时还需要把任务 assignee 的引用与自己识别的 Agent 身份对齐，否则错误的临时执行请求（fork）可能让 A 为 B 的任务启动 Executor，也就是受委派做具体工作的临时执行者。当前 fork 入口有这道防误派检查。[代码：身份匹配防护](https://github.com/oopslink/agent-center/blob/main/internal/agentruntime/executor_runtime.go)

### 一个字段名就能制造误解：IdentityMemberID 指的究竟是谁

当前 Agent 的 `identityMemberID` 很容易被读成 Member 行的主键。但字段旁的注释明确说明，它保存的是 identity-member 的 Identity ID，也就是 `agent-...` 这样的身份 ID。这说明统一语言不能只停在文档：同一个字段的名字、注释、DTO 和调用者的比较方式都需要一致。[Agent 身份关联字段](https://github.com/oopslink/agent-center/blob/main/internal/agent/agent.go)

运行时的 `identityRef()` 也值得读。它优先使用中心投影的 `agentRef`，缺失时退回配置里的 AgentID；而 Task.assignee 使用自己的 actor ref 命名空间。fork 入口的修订注释明确提醒，直接拿执行 Agent 的 ULID 比较 assignee，会把正常分派也判成已转派。[运行时身份引用](https://github.com/oopslink/agent-center/blob/main/internal/agentruntime/local_runtime.go) · [跨命名空间防护](https://github.com/oopslink/agent-center/blob/main/internal/agentruntime/executor_runtime.go)

这不是术语洁癖。身份混用会直接改变谁可以启动任务。更危险的是，它可能表现成“所有任务都没启动”，看起来像调度故障，实际却是不同 ID 空间的字符串比较。我的建议是把转换集中在显式的边界适配里，让日志同时记录执行 Agent ID 与业务 actor ref，并继续减少容易误读的命名。这个建议针对现有复杂度，不等于宣布当前每条兼容路径都能立即移除。

| 概念 | 主要回答 | 可以改变的内容 | 不应该替代它的东西 |
|---|---|---|---|
| Identity | 谁在行动 | 展示信息、账户状态 | Profile.name |
| Member | 在哪个组织、有什么成员角色 | 角色与成员状态 | “Tester”这样的自由文本标签 |
| 执行 Agent | 由什么配置与运行环境承接 | Profile、生命周期 | 一个临时 Executor ID |
| Task.assignee | 谁承担这项任务 | 显式重新分配 | 对话中的自称 |
| 上下文视图 | 此次判断可用哪些事实 | 范围、版本与候选筛选 | 同角色成员的全部历史 |

### 上下文边界比角色标签更难

假设负责测试的 Tester 要判断一版候选代码是否可交付。它需要看到需求、当前候选、相关修改、适用检查和旧回执为何失效。它们可能由不同角色生成。若系统按“只读同角色材料”供给上下文，Tester 会缺关键信息；若把整个团队历史原样塞入，又会遇到噪声、过期结论和权限问题。合理的选择单位应该是**当前决策需要什么证据**，再受身份和权限约束，而不是凭写入者的角色决定读者能否看见。

这也解释了为何“共享上下文”不是“共享一段大 prompt”。上下文必须有来源、版本和适用范围。当前系统的 Task、Conversation 和分层 Memory 为不同来源提供存储与引用，但如何拼出每个决策所需的最小充分证据，仍是设计与评估问题。[代码：Conversation](https://github.com/oopslink/agent-center/blob/main/internal/conversation/conversation.go) · [代码：Memory 作用域](https://github.com/oopslink/agent-center/blob/main/internal/cognition/memory/path.go)

**示例 · 同角色的旧证据，跨角色的新证据。** 验收者手里有两份报告，一份是另一位 Tester 为候选 A 签发的通过回执，一份是开发者为当前候选 B 运行检查所得的失败记录。如果只取同角色历史，界面会留下一份看似可信的绿色报告。按当前候选和权限取材料，验收者则有理由拒绝 B，并说明具体失败项。这里仍须核对检查是否覆盖合同，只换筛选顺序不会赋予任何人额外验收权。

![围绕当前候选选择材料的过程](assets/05-context-selection.png)

图 2：说明性情境。旧候选的通过报告不能遮蔽当前候选的失败记录；正文用 A、B 区分两个候选，筛选步骤是设计建议。

## 三、实现效果

### 固定机器身份后，名字和材料分别改变了什么

项目关于命名、角色与共享上下文的研究工作稿（编号 P3）把这些问题拆开：固定机器 ID 和权限，比较不同命名条件下的验收决策；另外比较不同上下文选择策略。其受控决策中，个人名的有无没有改变验收动作；当信息只按同角色来源提供时，8 类情境仅有 2 类具备必要信息。结论限于这些任务与材料，不能推出名字对长期团队体验没有价值。[研究工作稿 P3](https://github.com/oopslink/agent-center/blob/main/docs/plans/reports/papers-010/p3-role-shared-context/paper.md)

![不同信息选择策略能充分处置的情境数](assets/05-context-coverage.png)

图 3：依据 P3 表 7 重绘，展示材料的可判定上限。个人历史有一个情境可以仅凭当前失败拒绝，因此“足以处置 3/8”不等于“两项必要事实齐全 3/8”。

把两种问题分开计分，才能读懂上下文实验。验收者拿到旧候选的绿色回执时，请求补证是正确动作。用“回答合规”评分，它可以得满分。用“现在能否完成本轮验收”评分，它一次也没有判定当前候选。这两种结果可以同时成立。产品若只监测模型回答正确率，材料筛选造成的额外等待就会完全消失在报表里。

| 接收者看到的材料 | 当前可以采取的行动 | 系统还欠接收者什么 |
|---|---|---|
| 当前候选、匹配的合同和通过回执 | 在其授权范围内接受候选 | 保存判断所依据的版本 |
| 当前候选有匹配的失败证据 | 拒绝并指出缺口 | 将修复义务交回负责人 |
| 只有上一候选的回执 | 请求当前凭据 | 找到可授权读取的证据或安排检查 |

表中是按验收条件推演的三个场景。如果最后一行经常发生，优先检查材料是被权限限制、被角色筛选排除，还是压根没产生。这三类故障分别需要授权、检索和执行方面的修改。

### 名字变了，判断却没有跟着变

在论文的短情境实验中，全部获准记录和当前范围记录都能支持 8/8 类情境，两模型直接处置也都为 32/32。前者包含七条记录，后者三条。这个结果说明，当前范围筛选能减少材料；却没有证据表明它提高了这组任务的正确率。不能看到过滤器更精巧，就把它写成效果更好。[P3 表 7](https://github.com/oopslink/agent-center/blob/main/docs/plans/reports/papers-010/p3-role-shared-context/paper.md)

另一个更干净的对照固定机器 ID 和权限，只改变展示字段：缺省个人名、个人名、角色标签。三组拿到当前候选的跨角色凭据时，都是四次通过、四次拒绝；只拿到旧候选的同角色凭据时，都是八次请求补证。这里没有“人名增强团队协作”的效果，也没有“人名使模型犯错”的效果；真正改变能否直接判定的是凭据是否对应当前候选。

| 展示字段 | 仅有旧候选凭据 | 有当前候选凭据 |
|---|---|---|
| 无个人名 | 8 次请求补证 | 4 次通过、4 次拒绝 |
| 个人名 | 8 次请求补证 | 4 次通过、4 次拒绝 |
| 角色标签 | 8 次请求补证 | 4 次通过、4 次拒绝 |

表 2：P3 的 48 次首步处置。请求补证是合规动作，不应该为凑出差异被计作错误。我的产品判断据此收窄：名字应作为可用性和团队体验功能，而不应拿来论证权限或交付收益。

## 四、总结反思

稳定身份让任务归属可追踪，可读名字帮助操作者找到成员，这两项设计有各自的用途。走偏的地方是又期待命名解决跨会话的信息不足。验收者缺的是当前候选的证据，改名字不会补齐它。

### 从眼前这项验收，往回找需要的材料

以 Tester 验收为例，我会按下面的顺序取材料：先明确当前 Task 和候选，再读取适用合同与当前凭据，随后补充解释缺口所需的跨角色记录，最后才读较远的历史经验。每条材料仍需遵守权限；“与任务相关”不是绕过权限的理由。同角色可以作为检索线索，但不能成为硬过滤条件。

这个顺序还有一个工程好处：当判定失败时，可以说清楚是缺了候选、合同、凭据，还是材料过期。相比“给它更多上下文”这样的宽泛处方，这种缺口更容易补，也更容易做针对性测试。需要防止的不是跨角色读取本身，而是没有来源、没有版本、没有适用范围的事实混合。

### 再遇到“它是谁”，需要把问题问得更具体

写设计文档或排查故障时，我会要求一句话明确它谈的是哪一个层次：稳定 Identity、组织 Member 角色、执行 Agent 的进程和配置、还是当前任务上下文。再问两个不同问题：谁被授权行动？它拿到了哪些足以行动的材料？只有把两者分开，才能看清“角色看起来对，结果仍然错”的失败。

回到那个叫“后端小张”的成员，它仍然可以有一个容易记住的名字。但任务转派时要查稳定身份，执行操作时要查权限，判断交付时要查当前证据。**这几件事分别有了依据，名字才可以安心承担它自己的用途：让人更容易辨认和交流。** 下一篇会沿着证据继续往下，看看计划调整以后，已有成果是否也被带到了下一步。
