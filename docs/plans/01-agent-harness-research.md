## 1. 目标与结论边界

回答：**Agent Center 为什么整体没有达到预期？哪些方案在实际运行中不成立，哪些看起来合理却没有兑现收益，哪些机制值得保留或简化？**

研究起点是开发者对系统整体不成功的观察：一个 Agent 包含 Supervisor 与多个 executor，可能造成职责混淆；复杂工作流可能阻碍推进；DAG evolution 有用；持久命名身份可能不利于 context 共享，但角色分工可能有用；名字可能带来开发者情绪价值，对全自动交付的作用有限。

这些是待检验判断，不是预定结论。研究以失败复盘和工程取舍为目的，不要求提出创新点，也不以能否发表论文决定研究问题的价值。已有研究发现过的问题，若能解释本系统的失败，同样应作为主要结论。文献用于解释机制、寻找反例与可行替代，不作为新颖性筛选门槛。

保留顺利运行、有效门禁和有效evolution的反例，明确区分“当前实现有缺陷”“设计假设不成立”“收益不足以抵偿负担”与“证据尚不能判断”。不能因为最终有人把功能做出来，就把此前的自动化、协调和产品验收问题一并判为成功。也不能仅凭复杂或消息多就认定机制无用。当前研究不直接改变生产领域模型或工作流。

**2026-11-02范围修订：研究排除明显的系统bug导致的问题。** 实现合同冲突、键错配、未接线、调度/状态错误等仅保留为排除记录，不用于判定组织架构或流程设计的负效应。配置错配、正常外部等待和可能由bug导致但根因不清的片段保守单列；不能改称“复杂度问题”后重新纳入。按片段筛选，同一Plan中独立检查/共享事实的正证据仍可保留。模型语义判断、正常机制下的交接、知识选择与治理仍可研究，但必须排查替代解释。当前规则追溯约束002—006的使用，旧报告及原始数据不覆盖删除；详见[007协议修订](/Users/oopslink/works/research/agent-harness-study/run-001/identity-007/protocol-v2.md)。

每项方案按“原本承诺的收益 → 实际发生的过程 → 失败位置/额外负担 → 反例与替代解释 → 保留、简化、替换、停用或待定”形成可执行判断。交付质量、持续自主推进、人工兜底和维护负担分别评价；不可可靠量化时记录具体事件，不编造总成本或全自动完成率。

## 4. 分析单位与结果定义

- **交付目标及其失败—恢复过程**：允许跨Plan/Task承接，保留各时点验收范围；用于解释真实结果和负担。
- **Plan**：编排容器和抽样入口，不自动视为一个独立交付目标或独立试验。
- **Task**：领域工作单元。executor attempt 单独记录；实际执行标识须先核实，不把 Agent、Task 和 executor 混为一谈。
- **阻塞—恢复片段**：从可定位阻塞到有效进展、放弃或观察截止的过程；研究分析单位，不引入生产聚合。
- **Generation 转换**：父子 generation 的结构变化与前后证据，不将快照差异自动认定为 intervention。

“有效进展”定义为新增且可核验的代码、测试结果、交付证据或满足下游真实前置条件；改状态、改计划、发消息和模型自报均不单独构成有效进展。

结果分别记录：执行结束、可访问交付物、独立验收、集成、部署（仅适用任务）、后续已知回归。按任务原始交付契约判断，不强制所有任务部署；未知结果明确标为 unknown。

停滞候选初筛：出现 blocked、重复恢复动作，或在可观测执行区间连续 2 小时无有效进展。2 小时只是试点阈值，做 1/2/4 小时敏感性分析；排除预先安排的等待，另报人工等待与外部等待。数据不足时标为无法判断，不补造时间线。

## 6. 标注手册与证据要求

每个片段至少包含：Plan/Task/generation/执行引用、目标与契约、版本窗口、时间线、首个可见偏差、阻塞类型、控制动作、人工介入、结构变化、结果层级、成本可用性、替代解释、证据引用和置信度。

007起另记**设计效应纳入状态及理由**：明确bug排除、配置排除、根因不确定、正常外部条件、可纳入语义/设计过程、可纳入正证据、体验证据、仅机制说明。对原始片段和拟支持主张分别判定；检查“机制是否按设计运行”，缺证据时不假设已排除bug。排除数不能用来计算设计失败率。

初始多标签分类：

| 类别 | 可观察判据 |
|---|---|
| 职责或权限混淆 | 向错误角色索取交付、误认自身权限或执行环境，有具体操作或纠正记录 |
| 上下文断裂 | 必要信息在上游存在，下游未收到或误解；确认实际可见输入后才归类 |
| 流程往返 | 重复控制动作未产生新证据，且阻塞条件未变化 |
| 必要质量拦截 | 门禁阻止了可复现缺陷或不可验证交付 |
| 交付协议缺陷 | 实际工作与候选、持久文件、verdict 或 provenance 不一致 |
| 外部依赖/基础设施 | 权限、资源、网络、部署等外因；可与 harness 缺陷并存 |
| 有效结构调整 | 改变错误依赖、任务边界或职责后出现可验证进展 |
| 无效结构调整 | 仅重述、重复生成，或未解决阻塞原因；观察不足时不强判 |

每个结论至少有原始记录 ID/路径、时间、必要片段和推断说明；原始 trace、工具结果、人工评价与 agent 自报分开存放。模型只辅助检索和初标，不独自裁决因果或成功。

目标由两名人工标注者独立复核至少 20% 的正式样本，并覆盖全部机制类型；报告一致率、分类适用时的 Cohen’s κ、分歧与裁决过程。若无法取得第二名标注者，采用单人间隔复核并明确披露限制，不以两个 LLM 充当独立人工标注者。

## 7. 分析方法

1. **描述性分析**：分版本窗口报告覆盖、状态、等待、重复动作及成本分布，标明各指标的有效分母和缺失率。未标明 token 口径时不将 cache 与 input 简单相加。
2. **过程分析**：比较偏差发生、被发现、被干预及恢复的路径；寻找同机制的成功与失败对照。
   每个重点案例同时区分产品缺陷、harness自身制造的障碍、外部条件与人工接管；最终交付不自动抵消中间的机制失效。人工动作区分正常需求/授权决定与为流程纠错的兜底，不把所有人类参与都算作自动化失败。
3. **Evolution 分析**：区分任务拆分、错误前置条件删除、角色重分配、修复链添加、纯描述变更；核对父子快照和真实调度。分别评价下一有效进展和最终交付。
4. **敏感性分析**：变化停滞阈值；分开 known/unknown、迁移记录、人工纠正、基础设施故障；观察结论是否改变。
5. **关联分析约束**：generation 次数与成本或成功率的关联不等于效果。困难任务更易 evolution，已停滞任务才接受干预，均存在选择与时间偏差。按项目、任务类型和版本分层，样本足够时再做 Plan 层聚类区间估计；不把消息或片段当独立样本扩大 n。

不从单个案例推出因果效应。未完成任务在快照截止时作为右删失或 unknown 处理，不能全归失败；仅观察范围内的“无回归”不能写成持续可靠。

## 8. 后续受控实验候选

保留相同任务输入、模型版本、工具、权限、验证标准与总预算，随机化运行顺序，使用隔离仓库与固定起始提交；每条件重复执行。试点估计方差后再确定样本量、预算和停止规则。历史轨迹回放只验证具体边界行为，不替代端到端重跑。

| 实验 | 比较 | 控制与主要结果 |
|---|---|---|
| 执行结构 | Supervisor + 多 executor vs 更少层级的任务执行 | 保留相同职责覆盖与工具；测独立验收、协调错误、成本和人工干预 |
| 推进机制 | 现有流程 vs 简化控制步骤 | 保留等价质量检查；同时测漏放缺陷和无产出往返 |
| DAG evolution | 固定初始图 vs 允许证据驱动调整 | 两组具有相同失败信息与总预算；测最终交付及恢复成本 |
| 身份/角色 | 先仅切换名字，再单独切换记忆共享和角色契约 | 避免把匿名化、共享 context、去角色同时改变；测交付与信息遗漏 |

开发者情绪价值通过访谈、反思日志和体验比较独立研究；首轮只作为单开发者案例，不宣称普遍用户效应。
